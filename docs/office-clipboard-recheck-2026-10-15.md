# Office 클립보드 재확인 기록 (2026-10-15)

기준: main `5d6a6ac`, 기존 [Claude 인수인계](handoff-office-clipboard.md).
상태: **사용자가 보고한 반복 오류의 원인은 아직 확인하지 못했다. 제품 수정·새 릴리스 완료 기록이 아니다.**

## 환경과 사용자 확인

- 이 노트북에는 처음에 v1.9.4가 실행 중이었다. 공식 v1.9.6 설치 파일을 내려받아 SHA-256을 릴리스 자산 정보와 대조한 뒤 설치했다. 실행 중인 파일의 제품 버전은 `1.9.6+899618071fc9b1da5285ddaff23b40ac4ddcedc5`로 확인했다.
- Excel은 Office 15 / Excel 2013이다. 별도의 빈 통합 문서에 시험 문자열만 입력했다.
- 이전 인수인계의 "개발 PC에 피어가 없음"과 달리 이번 확인에서는 등록 피어가 두 대였다. 두 항목 모두 장치 ID가 있고, 이 노트북 자신의 ID·주소와 일치하지 않았다.
- 처음에는 두 피어 모두 IntraDrop 프로토콜 ping에 응답하지 않았다. 이후 사용자가 PC들을 켰고, 두 피어 모두 응답했다.
- 사용자는 증상이 **다른 Windows 11·Excel 2013 PC에서 발생하며 이 노트북에서는 아직 확인하지 않았다**고 답했다. 따라서 노트북에서 재현되지 않는 결과로 문제 PC의 해결을 단정할 수 없다.

## 실제 UI 시험 결과

Orca computer-use로 키 입력·셀 우클릭을 수행했다. Orca가 Excel 팝업의 작은 보조 창만 반환하는 경우에는 Windows computer-use의 접근성 트리로 실제 메뉴 항목을 확인했다. 클립보드 내용 읽기와 무관한 메타데이터 감시도 함께 실행했다.

| 조건 | 관찰 |
|---|---|
| v1.9.4 실행 중, 피어 연결 불가 | 시험 셀의 Ctrl+C 후 Excel 소유권과 복사 상태가 유지됐다. 우클릭 메뉴가 열렸다. |
| main의 캡처 코드만 실행, 네트워크 전송 없음 | 작은 셀 텍스트 읽기는 약 1~2ms, 10만 행 범위는 약 22ms였다. 관찰한 읽기에서 전후 클립보드 시퀀스가 같았다. 큰 범위는 기존 1MB 제한으로 공유되지 않았다. |
| 설치된 v1.9.6, 피어 연결 불가 | `NEW_196_COPY`를 C1에서 D1로 Ctrl+C/V하여 같은 값을 확인했다. `NEW_196_CUT`을 C2에서 E2로 Ctrl+X/V하여 E2의 새 값과 비워진 C2를 확인했다. |
| 설치된 v1.9.6, 피어 연결 불가 | 우클릭 메뉴가 약 49초 유지됐다. 기록상 `Net UI Tool Window`, 마우스 캡처 상태와 Excel 클립보드 소유권이 유지되다가 시험자가 Esc를 눌렀을 때 메뉴가 닫혔다. |
| 설치된 v1.9.6, 두 피어 ping 성공 | 새 시험 문자열을 복사하고 우클릭했다. 약 6분 14초 동안 메뉴·복사 상태와 Excel 소유권이 유지됐다. 시험자의 Esc 입력 후 메뉴가 닫혔다. |
| 현재 설정을 사용하는 별도 전송 검사 | 같은 시험 문자열에 대해 한 피어는 클립보드 적용 완료 응답을 보냈고, 다른 피어는 `IOException`을 반환했다. 후자의 구체적 원인은 이 결과만으로 확정하지 않았다. |
| Excel 메뉴가 열린 동안 셸 연결 변경 알림 1회 | 메뉴 닫힘이 재현되지 않았다. |
| 노트북의 복사 모드를 해제한 뒤 실제 수신 | 17:57:58에 소유자가 IntraDrop으로 바뀌고 수신 표식이 기록됐다. 17:59:36 감시 종료까지 추가 클립보드 변화는 없었다. 내용은 읽지 않았다. |

임시 캡처 추적 코드는 검사 후 제거했다. 제품 소스의 변경은 없다. 시험 통합 문서들은 저장하지 않고 닫았으며, 설치된 IntraDrop v1.9.6은 실행 상태로 남겼다. 화면·원시 로그·PC 이름·IP·장치 ID·암호는 저장소에 올리지 않았다.

## 진단 도구 보완

기존 `tools/watch-clipboard.ps1`은 클립보드 시퀀스가 바뀔 때만 기록했다. 메뉴가 닫힌 시점에 창 전환이 있었는지 구분할 수 없어 다음 메타데이터의 변화도 기록하도록 보완했다.

- 클립보드 소유 창·프로세스, 시퀀스 변화량, 형식.
- 전면 창·활성 창·포커스 창의 핸들과 클래스, 메뉴 플래그·마우스 캡처 여부.
- Ctrl 및 Ctrl+C/X/V, 좌우 마우스 버튼 상태. Ctrl 없는 일반 문자 키는 기록하지 않는다.
- `GetGUIThreadInfo` 성공 여부. `guiAvailable=False`를 정상적인 유휴 상태로 해석하면 안 된다.

`OpenClipboard`, `GetClipboardData`, OLE 클립보드 조회·쓰기, UI 입력은 사용하지 않는다. 창 제목이나 복사한 내용도 기록하지 않는다. 20ms 간격의 표본 기록이므로 매우 짧은 변화는 놓칠 수 있고, 소유자 기록만으로 실제 쓰기 호출자를 확정할 수는 없다. 특히 **소유자가 그대로인데 메뉴가 닫혔다고 해서 곧바로 지연 렌더 문제로 단정하지 말고 전면 창 전환도 확인해야 한다.**

검증:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test-watch-clipboard.ps1
git diff --check
```

Windows PowerShell에서 메타데이터 스냅샷 생성·로그 저장 검사와 실제 Excel 메뉴 열림/닫힘 관찰을 통과했다. 제품 소스를 바꾸지 않았으므로 전체 제품 테스트·새 설치 파일 빌드는 수행하지 않았다.

## 다음에 필요한 증거

### 사용자 후속 확인: 복사 직후 화면 이동

2026-10-15 후속 응답에서 사용자는 문제 PC에서 이번에는 복사·우클릭 취소가 발생하지 않았지만, **Ctrl+C 또는 Ctrl+X 직후 화면이 잠깐 스크롤됐다가 원래 위치로 돌아온다**고 보고했다. 원래 오류의 영구 해결을 확인한 결과는 아니다.

제품 코드를 다시 확인했으며 Excel의 스크롤·선택을 직접 조작하는 호출은 없었다. 일반 셀 복사는 네이티브 Unicode 텍스트 조회를 우선하고, 텍스트 형식이 없는 비트맵 복사만 OLE 경로를 사용한다. [Microsoft의 WM_RENDERFORMAT 문서](https://learn.microsoft.com/en-us/windows/win32/dataxchg/wm-renderformat)에 따르면 클립보드 조회는 원본 앱에 지연된 데이터 생성을 요청할 수 있다. 따라서 Excel의 데이터 생성 과정에서 화면이 움직일 가능성은 가설로 남아 있지만, 이 문서가 Excel의 스크롤 증상이나 그 원인을 입증하는 것은 아니다.

기존 Excel 테스트는 복사·잘라내기 상태, 셀 값과 메뉴 유지만 검사하며, 잠깐 움직였다 돌아오는 화면 위치는 검사하지 않는다. 현재 감시 스크립트 역시 화면의 스크롤 위치나 IntraDrop 내부의 읽기 시작·종료 시각은 기록하지 않는다. 이 로그만으로 화면 움직임이 없었다거나 읽기가 원인이라고 단정할 수 없다.

사용자에게 Ctrl을 누른 채 C/X를 한 번 누르고 Ctrl만 2초 더 유지했을 때의 시점을 확인했다. 답변은 **Ctrl을 누르고 있는 동안 화면이 움직인다**였다. v1.9.6 코드상 전면 Office가 인식되고 `GetAsyncKeyState(VK_CONTROL)`이 눌림을 반환하면 새 자동 읽기는 시작되지 않는다. 따라서 "Ctrl을 놓은 뒤의 자동 읽기 때문에 발생한다"는 가설은 약해졌다.

이는 IntraDrop의 영향을 배제하는 결과는 아니다. 보호 검사 전에 이미 진행 중이던 읽기, 실제 실행 버전·전면 앱·키 상태 인식 차이는 확인되지 않았다. 수신 보호는 Ctrl 단독이 아닌 Ctrl+C/X/V 조합을 보지만, Excel이 클립보드를 소유하면 별도의 소유권 보호가 적용된다. 메타데이터 감시 스크립트만으로 내부 읽기나 보호 판정 실행 여부를 확인할 수는 없다.

이전의 취소 현상과 이번의 짧은 화면 움직임을 구분하기 위해, 문제 PC에서 IntraDrop을 종료한 뒤 같은 파일·셀의 Ctrl+C/X에도 화면 움직임이 남는지 확인했다. 사용자는 **종료해도 스크롤 현상이 남는다**고 답했다. 이번 화면 움직임은 IntraDrop이 실행 중이어야만 발생하는 현상이 아니므로, 이것만을 근거로 자동 공유 코드를 변경할 수 없다. Excel 자체 동작이나 다른 프로그램의 영향 등 구체적인 원인은 확인되지 않았다. 또한 이 결과로 이전의 복사 취소·우클릭 메뉴 닫힘까지 IntraDrop과 무관하다고 결론 내릴 수는 없다.

화면 위치를 강제로 복원하거나 지연 시간을 임의로 늘리는 수정은 넣지 않았다. 원인이 확인되지 않았고 사용자가 의도한 스크롤·선택을 되돌릴 위험이 있기 때문이다.

이전의 복사 취소·이전 내용 붙여넣기·우클릭 메뉴 닫힘이 다시 발생하면, 문제 PC에서 다음 명령을 실행하고 빈 Excel 문서에서 새 값을 입력한 뒤 Ctrl+C, Ctrl+X, 셀 우클릭을 재현한다. 복사 원본 내용 대신 증상 시각과 메타데이터를 확인한다. 종료 상태에서도 남는 짧은 화면 움직임과는 구분해 기록한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/watch-clipboard.ps1 -Seconds 120
```

로그는 기본적으로 `%TEMP%\IntraDrop-clipboard-watch.log`에 저장된다. PC 이름과 프로세스 메타데이터가 있으므로 원시 로그를 공개 이슈에 그대로 게시하지 않는다. 상대 컴퓨터가 연결된 조건에서의 재현 결과와 함께 읽어야 한다.

내용 기반의 영구 중복 제거는 아직 넣지 않았다. 같은 내용을 다시 복사해서 재전송하는 기존 동작을 막을 수 있고, 비교를 위해 Office 클립보드를 추가로 읽는 것 자체가 간섭을 만들 수 있기 때문이다. 자기 피어 필터·시퀀스 처리 변경도 이번 현상의 원인으로 확인되지 않았다.
